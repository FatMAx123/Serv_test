# Аудит №26: Worker Threads Offloading (100% Утилизация 2 vCPU)
**Project Steam — Серверное Ядро MMO (2 vCPU Оптимизация под 1500–2000 CCU)**
**Статус**: `IMPLEMENTED`
**Дата**: 24 сентября 2026 г.

---

## 1. Введение и Архитектурная Цель

В ходе оптимизации серверного ядра на Уровнях 1–4 была достигнута высочайшая отзывчивость главного цикла тика (10 Hz): задержка Event Loop упала до **10.04 мс** при 500 CCU, а Spatial Grid ускорился в 5.3 раза на C++ SIMD.

Однако на 2-ядерном сервере (2 vCPU) процесс Node.js по умолчанию является однопоточным:
- **vCPU 1**: Несет 100% нагрузки сетевого транспорта, боевого цикла, физики и логики мобов.
- **vCPU 2**: Простаивает на 85–90%, не участвуя в игровом цикле.

**Цель Уровня 5**: Задействовать 2-е ядро vCPU на полную мощность через механизм **Node.js `worker_threads`**, вынеся дисковый I/O, атомарную запись профилей игроков, клановых складов (CWH), бэкапы и тяжелую сериализацию JSON в фоновый пул воркеров.

## 2. Архитектура Фонового Воркера Персистентности

### 1) Изоляция V8 Isolate на vCPU 2 (`server/workers/persistence-worker.js`)
- Воркер запускается в независимом потоке операционной системы через `new Worker(...)`.
- Поток автоматически диспетчеризируется планировщиком ядра Linux на второе доступное ядро процессора (vCPU 2).
- Воркер имеет собственный изолированный кусок памяти (V8 Isolate) и собственный цикл событий Event Loop.

### 2) Неблокирующий протокол задач (Message-Passing)
- Главный поток сбрасывает задачу сохранения через `worker.postMessage`:
  ```javascript
  worker.postMessage({
    id: ++nextJobId,
    type: 'write_atomic',
    file: '/var/www/project-steam/data/player_1.json',
    label: 'player_1',
    payload: profileData, // или готовый json
    makeBak: true
  });
  ```
- **Затраты главного потока**: отправка сообщения занимает **< 0.05 мс**.
- **Работа воркера на vCPU 2**:
  1. `JSON.stringify(payload)` в отдельном потоке (освобождает 10–25 мс V8 кучи главного потока).
  2. Запись во временный файл `.tmp` через `fs.promises.writeFile`.
  3. Физический сброс кэшей ОС на диск `fileHandle.sync()`.
  4. Создание архивной копии `.bak`.
  5. Атомарное переименование `rename(tmp, file)`.
  6. Отправка подтверждения обратно в главный поток `{ id, ok: true }`.

### 3) Graceful In-Memory Fallback
- При недоступности `worker_threads` (или в изолированных тестовых песочницах) система прозрачно переходит в синхронный режим, гарантируя 100% обратную совместимость со всеми существующими тестами.
