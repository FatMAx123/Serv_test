1. Категория P0: Критические Сбои и Безопасность

🔴 [P0-1] Спуфинг IP-адресов на MasterGateway и Лимиты Соединений
P0 · CRITICAL · SECURITY

Проблема: MasterGateway проксировал соединения на Zone Workers без надежного вычисления IP клиента. Злоумышленник мог подставить произвольные заголовки x-forwarded-for и x-real-ip, обходя баны по IP и подменяя адрес в логах аудита. Лимит MAX_CONNS_PER_IP действовал только в standalone-режиме, а в кластере счетчик сокетов на IP отсутствовал.

Решение: Внедрена санитизация заголовков в uwsApp.any с немедленным удалением клиентских заголовков x-real-ip, x-forwarded-for, forwarded и вычислением через SEC.resolveClientIp(res, headers). В ClusterManager добавлен реестр this.ipConnections с лимитом сокетов на IP (HTTP 429 при превышении). Прокси-сокеты GatewaySocketProxy и события client_raw передают проверенный clientIp в профиль p.clientIp.

// server/cluster-manager.js: санитизация заголовков и защита от спуфинга
delete headers['x-real-ip'];
delete headers['x-forwarded-for'];
delete headers['forwarded'];
headers['x-real-ip'] = clientIp;
🔴 [P0-2] Рассинхронизация In-Memory Реестров (Mod, AccountKeys, GM)
P0 · CRITICAL · SYNC

Проблема: Санкции модерации (баны, муты, блокировки IP) и кодовые ключи AccountKeys сохранялись только в памяти воркера, где была выполнена команда. На остальных воркерах забаненный нарушитель мог продолжать играть, а смена кодовых слов не доходила до соседних зон.

Решение: В IpcHub добавлены каналы MSG_MOD_SYNC, MSG_ACCOUNT_KEY_SYNC, MSG_GM_SYNC. Модули Mod и AccountKeys оснащены методами setIpcHub(hub) и applySync(). На всех воркерах слушается mod_sync, мгновенно принудительно разрывающий сокеты заблокированных нарушителей онлайн.

// server/server.js: кросс-воркерный бан и разрыв соединения
clusterIpc.on('mod_sync', (payload) => {
  Mod.applySync(payload.action, payload.target, payload.payload);
  if (payload.action === 'ban' || payload.action === 'ban_ip') {
    for (const [, pl] of players) {
      if (pl && (pl.yid === payload.target || pl.clientIp === payload.target)) {
        send(pl, { t: 'banned', reason: payload.payload.reason });
        if (pl._ws) try { pl._ws.close(); } catch (_) {}
      }
    }
  }
});
🔴 [P0-3] Таргетинг Саппорт-Скиллов на Союзников и Очистка Ядов `eng_cure_toxin`
P0 · CRITICAL · COMBAT

Проблема: Заклинания исцеления (op_heal, heal) и баффы с target: 'target' при применении к союзнику обрабатывались через ветку враждебной PvP-атаки, вызывая проверку защиты от магии (M.Def), PvP-флаг и отсутствие лечения. Умение eng_cure_toxin не имело обработчика снятия дебаффов яда и коррозии.

Решение: Добавлена функция isSupportSkill(), определяющая исцеляющие, усиливающие и антидотные заклинания. Таргет союзника разрешается по переданному msg.pid с проверкой живого состояния, дистанции и зоны видимости LoS. Умение eng_cure_toxin корректно удаляет яд и коррозию без входа в боевой пайплайн.

// server/server.js: целевое исцеление союзника или пати
if (isSupportSkill(skill, def)) {
  let target = p;
  if (msg.pid != null) {
    const ally = players.get(msg.pid);
    if (ally && !ally.dead && Math.hypot(p.x - ally.x, p.z - ally.z) <= castRange) target = ally;
  }
  // Применение хила, баффа или снятия ядов (curePoison)
}
🔴 [P0-4] Защита Кланового Хранилища (CWH) от Гонок и Дюпа в Кластере
P0 · CRITICAL · EXPLOIT

Проблема: Операции с клановым складом (`cwh_put`, `cwh_take`) были технически разрешены на всех воркерах кластера. Одновременное изъятие одинакового предмета сокланами в городе (Воркер 1) и в поле (Воркер 2) создавало состояние гонки и дюп ресурсов.

Решение: Все операции CWH жестко изолированы исключительно на городском воркере 1 (Town Zone). Любая попытка доступа к CWH на полевом воркере немедленно отклоняется с ошибкой cwh_fail: town_only.

// server/handlers/clan-handler.js: ограничение зоны кланового склада
if (process.env.IS_CLUSTER_WORKER === '1' && process.env.WORKER_INDEX !== '1') {
  send(p, { t: 'cwh_fail', reason: 'town_only', npcId: npc.id });
  return;
}

2. Категория P1: Боевые Формулы, Эксплойты Состояний и Изоляция

🟡 [P1-1] Расчет Урона Периодических Эффектов (PvP DoT)
P1 · HIGH · COMBAT

Проблема: Формула тика DoT рассчитывала урон как долю от p.maxHp * frac, где frac = +e.dps. Умения игроков задавали dps: 35, что приводило к умножению maxHp * 35 (35 000 урона за секунду) и мгновенному ваншоту.

Решение: Введено четкое разделение: если dps >= 1, наносится плоский урон умения игрока (Math.floor(+e.dps) = 35 ед.). Если dps < 1, наносится процентный урон от монстров (доля от maxHp в коридоре 1%..12%).

🟡 [P1-2] Пассивные Бонусы и Умение `op_quick_hands` для Всех Типов Оружия
P1 · HIGH · BALANCE

Проблема: В `combatPack` пассивная прибавка к скорости атаки учитывалась только при условии isFistPack, лишая Операторов с мечами, молотами, луками и кинжалами бонуса умения «Быстрые руки». В возвращаемом объекте отсутствовали поля blockRate, rangeBonus, explosiveDamage.

Решение: Умение op_quick_hands накапливается в базовый attackSpeed, а eng_robe_step — в fistAtkSpeed. Формула скорости атаки в боевом пакете переведена на канонический вид: pasAtkSpd = (pas.attackSpeed || 0) + (isFistPack ? pas.fistAtkSpeed : 0).

🟡 [P1-3] Сплошная Блокировка Действий в Состоянии Занятости (`p.trade || p.store`)
P1 · HIGH · EXPLOIT

Проблема: Игроки во время торговли или стоя в личной торговой лавке могли использовать зелья/свитки, телепортироваться, завершать квесты или покупать баффы, что создавало потенциальные окна для рассинхронизации инвентаря и дюпов.

Решение: В обработчики use, doTeleport, doBuffBuy, doQuestComplete и doClanCreate интегрированы строгие проверки if (p.trade || p.store) return fail('busy').

🟡 [P1-4] Кросс-Воркерная Видимость Друзей/Кланов и Синк Пати при Дисконнекте
P1 · HIGH · SOCIAL

Проблема: Друзья и сокланы на других воркерах кластера отображались оффлайн. При разрыве соединения игрока в detachPlayer пати не синхронизировалась на удаленные воркеры, оставляя сопартийцев в группе-призраке.

Решение: clanPayload и friendsPayload опрашивают глобальную директорию через ctx.clusterIpc.isPlayerOnline(). Метод detachPlayer при дисконнекте вызывает экспортированные broadcastPartySync и broadcastPartyDisband.

3. Категория P2: Оптимизация IPC и Защита Данных

🔵 [P2-1] Base64-Сериализация Бинарных Буферов по Шине Node IPC
P2 · MEDIUM · PERFORMANCE

Проблема: Штатная сериализация process.send(Buffer) разворачивает бинарные данные в тяжеловесные JSON-массивы целых чисел {"type":"Buffer","data":[...]}, что приводило к 4-кратному раздуванию трафика между мастер-шлюзом и ядрами зон.

Решение: В GatewaySocketProxy.prototype.send буферы кодируются в base64 (isBase64: true), а в ClusterManager восстанавливаются через Buffer.from(data, 'base64'). Экономия объема сообщений составляет до 65–70%.

🔵 [P2-2] Зональный Шардинг при Логине: Устранение Промежуточного Спавна
P2 · MEDIUM · OPTIMIZATION

Проблема: Персонажи, вышедшие из игры в полевых зонах, при авторизации всегда сначала спавнились на городском воркере 1, создавая ненужную нагрузку на AOI города перед передачей в целевой воркер.

Решение: В doLoginInner интегрирована мгновенная проверка ZS.getWorkerForCoords(p.x, p.z): если координаты принадлежат другому воркеру, сессия немедленно передается через initiateClusterHandoff.

🔵 [P2-3] Расширение Регулярного Выражения `DATA_PRIVATE`
P2 · MEDIUM · SECURITY

Проблема: Сервер статики не фильтровал резервные копии редактора и дампы с расширениями .backup, .bak, .tmp, создавая риск утечки служебных файлов при прямом HTTP-запросе.

Решение: Паттерн обновлен до /(^|[\/\\])(local_[^\/\\]*\.json|.*\.bak|.*\.backup(\..*)?|.*\.tmp(\..*)?|editor-overrides\.backup.*)$/i в cluster-manager.js и server.js.

🔵 [P2-4] Полноценный Антиспам-Фильтр Гостей (`guest_` и `local_`)
P2 · MEDIUM · ANTI-SPAM

Проблема: Проверка антиспама накладывалась только на префикс guest_, пропуская локальные временные сессии с префиксом local_.

Решение: Условие объединено: p.yid.startsWith('guest_') || p.yid.startsWith('local_'), что полностью ликвидировало спам с временных аккаунтов.
