2. VULN-PROD3-01: Загрязнение реестра заточки (Loot, Shop, Craft)

Смешивание +0 предметов с модифицированными (+N) в общем счетчике High / CWE-840, CWE-662
Файлы: server/server.js (строки 1983–1997, 5513), server/handlers/npc-services-handler.js (строка 100)

В архитектуре инвентаря Lineage 2 Classic предметы хранятся плоскими счетчиками (p.inv[itemId] = count), а реестр заточки привязан к p.plusById[itemId]. Каноническое правило plusMoveOk запрещает нахождение в одной ячейке смешанных копий (обычных и отточенных). Однако при подборе лута с земли проверка if ((L.plus | 0) > 0) активировалась только если выпадающий лут имел заточку. Если на земле лежал +0 предмет, а у игрока уже был меч +5, предмет досыпался в инвентарь без проверки, создавая стек из двух мечей с признаком +5, что наглухо блокировало дальнейший оборот или приводило к дюпу при переносе на склад.

- if ((L.plus | 0) > 0) { - if (!plusMoveOk(fromCounts, fromPlus, p.inv, p.plusById, L.itemId, L.count, ...)) { ... } - } + const heldPlus = (p.plusById && (p.plusById[L.itemId] | 0) > 0) ? (p.plusById[L.itemId] | 0) : 0; + const eqPlus = equippedPlus(p, L.itemId); + if ((L.plus | 0) > 0 || heldPlus > 0 || eqPlus > 0) { + if (!plusMoveOk(fromCounts, fromPlus, p.inv, p.plusById, L.itemId, L.count, { toLocked: equippedCount(p, L.itemId), toExtraPlus: eqPlus })) { + send(p, { t: 'loot_fail', lid, reason: 'enchanted' }); + return; + } + }

3. VULN-PROD3-02: Стирание заточки экипировки при продаже копии торговцу

Ложное удаление реестра заточки экипированного оружия High / CWE-840
Файл: server/handlers/npc-services-handler.js (строки 132–136)

В обработчике продажи предметов NPC doShopSell содержалась строка: if (p.inv[itemId] == null && p.plusById) delete p.plusById[itemId];. Если игрок экипировал заточенный меч +10, а в инвентаре имел запасную копию +0 меча того же типа, продажа запасного меча обнуляла инвентарный счетчик и безвозвратно удаляла запись p.plusById[itemId], игнорируя надетый предмет!

- if (p.inv[itemId] == null && p.plusById) delete p.plusById[itemId]; + clearPlusIfGone(p, itemId); // Проверяет как инвентарь, так и надетые слоты (equippedCount)

4. VULN-PROD3-03: Обход блокировки Trade/Store в Learn и Upgrade

Параллельное расходование чертежей и ценных ресурсов во время торговли High / CWE-840, CWE-362
Файлы: server/server.js (L5524-5542), server/handlers/skill-learn-handler.js (L190-246)

В то время как обработчики craft, equip и enchant блокировались при открытом трейде или частной лавке, обработчики case 'learn' (списание рецепта) и case 'device_upgrade' (списание сотен единиц железа, угля и стали) не проверяли флаги p.trade и p.store. Это создавало возможность списывать предметы, уже заблокированные в торговом окне, вызывая отрицательные балансы и гонки синхронизации.

+ if (p.trade || p.store) { send(p, { t: 'msg', text: 'Заняты обменом или торговлей.' }); break; } + if (p.trade || p.store) { send(p, { t: 'device_upgrade_fail', reason: 'busy' }); break; }

5. VULN-PROD3-04: Гонка готовности в сделке TradeExecute

Отсутствие вызова TradeReady в атомарной транзакции переноса High / CWE-362
Файл: server/handlers/trade-handler.js (строки 207–217)

Валидация условий готовности игроков (живы ли оба, нет ли PvP-флага, не началась ли дуэль, в пределах ли 50 метров) происходила только на шаге нажатия кнопки подтверждения (doTradeConfirm). Однако на входе в исполняющую транзакцию tradeExecute(p, q) проверка отсутствовала. Если один из игроков умирал или получал PvP-флаг от удара моба/ПК прямо в момент подтверждения вторым игроком, обмен все равно исполнялся.

+ if (!tradeReady(p, q, 'trade_fail')) { + closeTrade(p, 'not_ready'); + return; + }

6. PERF-PROD3-01: Переполнение хэша Spatial Grid в //teleport

16-битное сворачивание координат за пределами мира в нулевые ячейки города Medium / CWE-190, CWE-840
Файлы: server/handlers/gm-handler.js (L128–140), server/spatial-grid.js (L34–36)

Формула хэширования координат spatialGrid._key упаковывает координаты макро-ячеек в 16 бит с маской & 0xFFFF. При вызове GM-команды //teleport с экстремальными координатами (> 3500 км) происходило переполнение 16 бит, отображающее удаленную сущность в AOI жителей стартовой деревни острова. Решение — строгий clamp координат мира [-20000, 20000] метров.

7. BUG-PROD3-01: Превышение капы MAX_FRIENDS в DoFriendAccept

Раздувание массива контактов друзей свыше лимита 50 Medium / CWE-770
Файл: server/handlers/social-handler.js (строки 203–225)

Лимит MAX_FRIENDS = 50 проверялся только при исходящем добавлении (doFriendAdd). Если игрок получал запрос, а затем заполнял список через другие заявки, подтверждение старого запроса (doFriendAccept) безусловно пушило контакт в массив, превышая лимит 50 записей.
