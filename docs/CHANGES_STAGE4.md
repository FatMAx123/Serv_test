# Этап 4.1 — гостевые токены и утечка yid (C4, H3)

## Что сделано
- **C4: yid других игроков больше не уходит клиентам.** Из пакетов `clan` (`members[].yid`, `leaderYid`) и `clan_status` (`yid`) убраны внутренние id. Клиент их не использовал.
- **H3: случайные отзываемые токены.** Раньше токен гостя с ключом = HMAC(захардкоженная соль, хэш ключа): вечный, один на все устройства, отозвать нельзя.
  - При вводе ключа выдаётся новый случайный токен (32 байта). Его хэш добавляется в `guestTokenHashes` всех персонажей аккаунта, до `GUEST_TOKENS_MAX` (по умолчанию 5) устройств, старые вытесняются.
  - Токены хранятся в профилях (БД), поэтому работают и в кластере.
  - Смена ключа (`/api/auth/set-codeword`) отзывает все токены аккаунта и возвращает новый `guestToken`.
- **Миграция.** Старый вычисляемый токен принимается, пока не задано `GUEST_LEGACY_TOKENS=0`, и сразу заменяется: сервер отдаёт новый токен в `welcome.guestToken` и в ответах `/api/chars*`, а клиент (`net-ws.js`, `char-select.js`) сохраняет его.
- **TOFU.** Старый аккаунт с персонажами, но без единого хэша токена, по-прежнему закрепляет токен первым входом, но теперь каждый такой случай пишется в лог (`guest_tofu`). `GUEST_TOFU=0` запрещает это. Новые гости без персонажей не затрагиваются.
- **Гонка в enterKey.** Запись токенов обновляет и онлайн-игрока в памяти, поэтому его сохранение больше не затирает новый токен.

## Новые переменные окружения
| Переменная | Значение |
|---|---|
| `GUEST_TOKENS_MAX` (5) | сколько устройств (токенов) хранить на аккаунт |
| `GUEST_LEGACY_TOKENS=0` | перестать принимать старые вычисляемые токены |
| `GUEST_TOFU=0` | запретить закрепление токена старыми профилями без хэша |

## Рекомендуемый порядок выкладки
1. Выложить с настройками по умолчанию: активные игроки автоматически получат новые токены.
2. Через 2–4 недели задать `GUEST_LEGACY_TOKENS=0` и `GUEST_TOFU=0`. Игроки, которые так и не зашли, войдут повторным вводом ключа.

## Тесты
- `tests/smoke-guest-tokens.js`: 19/19 по умолчанию, 17/17 с `PHASE=strict` (сервер с `GUEST_LEGACY_TOKENS=0 GUEST_TOFU=0`).
- Регресс: `smoke-security` 9/9, `smoke-editor-save` 13/13, `smoke-items` 13/13, `unit-editor-queue`.

# Этап 4.2 — секреты ключей из окружения (H3)

## Что сделано
- **Секреты.** `KEY_PEPPER`, `KEY_VAULT_SECRET` (и по желанию `KEY_PREHASH_SALT`, `KEY_KDF_SALT`, `KEY_KDF_ROUNDS`) берутся из env. Встроенные значения остались только для миграции.
- **Production без секретов не стартует.** Если `KEY_PEPPER` и `KEY_VAULT_SECRET` не заданы, короче 32 символов или совпадают со встроенными, сервер падает с FATAL. Временный обход: `ALLOW_DEFAULT_KEY_SECRETS=1`.
- **Автоперешифровка реестра.** При старте реестр пробуется расшифровать текущим `KEY_VAULT_SECRET`, затем `KEY_VAULT_SECRET_OLD`, затем встроенным. Если подошёл старый ключ:
  - старый конверт сохраняется в `account_keys_backup_<builtin|old>` (system_state / `data/*.json`);
  - реестр сразу перешифровывается текущим ключом. В кластере это делает только мастер-процесс.
  - Если не подошёл ни один ключ, реестр не трогается, а `enter-key` отвечает `busy`.
- **Ленивая миграция хэшей.** Хэш ключа одновременно служит логином, пересчитать его без самого ключа нельзя. Поэтому:
  - ключ ищется по новому хэшу, затем по старым параметрам (`KEY_*_OLD` или встроенным), затем по sha256-legacy;
  - найденный по старому хэшу ключ при входе переписывается на новый;
  - при старте в лог пишется прогресс: `ключей на текущих параметрах: X из Y`;
  - старый хэш сохраняется в записи, поэтому выданные от него legacy-токены работают до `GUEST_LEGACY_TOKENS=0`.
  - `KEY_ALLOW_OLD_HASHES=0` выключает приём старых хэшей. Ключи, которые так и не мигрировали, после этого не войдут, поэтому включать его стоит, только когда в логе почти «Y из Y».
- **Исправлено (дефект 4.1).** Если ключ создавал новый аккаунт без персонажей, выданный токен не принимался: хэши токенов хранились только в профилях. Теперь они хранятся и в зашифрованной записи ключа в реестре.

## Как выкладывать на живой сервер
1. Сгенерировать два секрета: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`.
2. Задать `KEY_PEPPER=<1>` и `KEY_VAULT_SECRET=<2>` и перезапустить. В логе должны появиться:
   - `реестр перешифрован текущим KEY_VAULT_SECRET (был: builtin)`;
   - `ключей на текущих параметрах: 0 из N`.
3. Хранить секреты в менеджере секретов, не в репозитории. Если `KEY_VAULT_SECRET` потерять, реестр не расшифровать.
4. Когда прогресс близок к N (или через 1–3 месяца), задать `KEY_ALLOW_OLD_HASHES=0`.
5. Смена секретов в будущем: старые значения перенести в `KEY_PEPPER_OLD` / `KEY_VAULT_SECRET_OLD`, новые — в основные переменные.

## Новые переменные окружения
| Переменная | Значение |
|---|---|
| `KEY_PEPPER` | обязателен в production, ≥32 символов |
| `KEY_VAULT_SECRET` | обязателен в production, ≥32 символов |
| `KEY_PEPPER_OLD`, `KEY_PREHASH_SALT_OLD`, `KEY_KDF_SALT_OLD`, `KEY_KDF_ROUNDS_OLD` | прежние параметры хэша (по умолчанию встроенные) |
| `KEY_VAULT_SECRET_OLD` | прежний ключ реестра |
| `KEY_ALLOW_OLD_HASHES=0` | перестать принимать старые хэши |
| `ALLOW_DEFAULT_KEY_SECRETS=1` | временно разрешить production без секретов |

## Тесты
- `tests/smoke-key-secrets.js`: 23/23. Сам поднимает сервер 4 раза: встроенные секреты → новые (перешифровка и миграция) → `KEY_ALLOW_OLD_HASHES=0` → неверный ключ реестра, плюс проверка FATAL в production.
- Регресс: `smoke-guest-tokens` 19/19 и strict 17/17, `smoke-security` 9/9, `smoke-editor-save` 13/13, `smoke-items` 13/13, `unit-editor-queue`.

# Этап 4.3 — H2: логин отдельно от ключа

## Что было
Ключ был одновременно логином и паролем: глобально уникальный, хэш без соли на аккаунт, перед хэшированием переводился в нижний регистр (требование заглавной буквы ничего не давало). Подсказка «ключ занят» при создании работала как оракул существования ключа.

## Что сделано
- **Логин + ключ.** Новые аккаунты создаются только с логином (3–24 символа `a-z 0-9 _ . -`, регистр не важен, уникален). Ключ — секрет, регистр важен, не обязан быть уникальным, не может содержать логин.
- **Хэш v3:** `HMAC-SHA256(KEY_PEPPER, login + key)` → `scrypt(N=16384, r=8, p=1)` со случайной солью 16 байт на аккаунт; формат `sc1$N$hex`, сравнение в постоянное время. Записи хранятся в зашифрованном реестре в `accounts` (логин → `{yid, salt, h, pp, tokens, legacyKeyHashes}`).
- **Лимит на логин:** 10 неудач за 15 минут с любых IP → логин заблокирован на 15 минут (против распределённого перебора). IP-лимиты остались.
- **Старые аккаунты не ломаются:**
  - вход одним ключом (без логина) работает как раньше, ответ содержит `needLogin: true`, меню предлагает привязать логин (режим `mode: 'link'`) или нажать «Позже»;
  - ввод свободного логина + старого ключа (`mode: 'any'`/`'login'`) тоже переводит старый аккаунт на логин;
  - при переводе старый хэш остаётся в `legacyKeyHashes` — ранее выданные legacy-токены работают до `GUEST_LEGACY_TOKENS=0`;
  - `KEY_ALLOW_KEYONLY=0` — финал: вход без логина выключен. Прогресс в логе: `аккаунтов с логином: X из Y`.
- **Смена pepper / сложности:** для v3 хранится id pepper (`pp`); запись по `KEY_PEPPER_OLD` принимается (пока не `KEY_ALLOW_OLD_HASHES=0`) и перехэшируется при входе. Рост `KEY_SCRYPT_N` тоже применяется при входе.
- **API:** `enter-key`, `login-codeword`, `set-codeword` принимают `login`. `set-codeword` для старого аккаунта требует логин и переводит его на v3; `code_taken` для новых аккаунтов больше нет. `codeword-status` возвращает `hasLogin`/`login` (только владельцу).
- **Клиент:** поле «Логин» в окне входа, шаг «Придумайте логин» после входа старым ключом, новые тексты RU/EN.

## Новые переменные окружения
| Переменная | Значение |
|---|---|
| `KEY_ALLOW_KEYONLY=0` | запретить вход без логина (старые аккаунты) |
| `KEY_SCRYPT_N` | сложность scrypt, по умолчанию 16384 |
| `KEY_LEGACY_CREATE=1` | только dev-тесты: создавать аккаунты старого формата (в production игнорируется) |

## Тесты
- `tests/smoke-key-login.js` (новый): 40/40. Создание, вход, регистр, перевод старых аккаунтов (`link`/`any`), отсутствие `code_taken`, соль/хэш в реестре, смена ключа с отзывом токенов, блокировка логина, смена pepper, `KEY_ALLOW_OLD_HASHES=0`, `KEY_ALLOW_KEYONLY=0`.
- Обновлены под логин: `smoke-guest-tokens` (сервер с `KEY_LEGACY_CREATE=1`; 19/19, strict 17/17), `smoke-key-secrets` (23/23), `smoke-prod`.
- Регресс: `smoke-security` 9/9, `smoke-editor-save` 13/13, `smoke-items` 13/13 (тесту нужен `MOD_SECRET` и в окружении самого теста), `unit-editor-queue`.
- Окно входа проверено в headless Chromium: вход старым ключом → шаг привязки логина → логин привязан; занятый логин → «Этот логин уже занят».

# Этап 4.4 — H7 (данные редактора — JSON) и E13 (атомарная запись PNG террейна)

## Что было
- **H7.** Каждое сохранение сцены генерировало **исполняемый** `client/js/editor-overrides-data.js` (≈1 МБ кода с данными внутри), который выполнялся у всех игроков. Ошибка экранирования или подмена данных = выполнение кода у каждого игрока (XSS-эквивалент).
- **E13.** PNG покраски террейна писались `writeFile` напрямую в `client/data` и `shared`: при сбое посреди записи файл обрезался, а два слоя и две копии могли разойтись. Плюс эти PNG отдавались с `immutable` на год без версии в URL — игроки не видели новую покраску.

## Что сделано
- **Данные сцены — только JSON.** Сервер пишет `shared/editor-overrides.json` и `client/data/editor-overrides.json` одной атомарной операцией (оба во временные файлы → `rename`), плюс `dist/client/data/` если есть. Исполняемый JS больше не генерируется.
- **`client/js/editor-overrides-data.js` — статический загрузчик** (≈3 КБ, в репозитории, сервер его не трогает): `fetch('../data/editor-overrides.json')` → те же `window.EDITOR_OVERRIDES_DATA/REV`, `WorldMetrics.applyEditorOverrides`, хваты оружия. `boot.module.js` ждёт `window.__PS_EDITOR_OVERRIDES_READY` до `world-metrics`; если JSON не загрузился — та же ошибка загрузки, что и раньше («не загрузился data/editor-overrides.json»).
- **Миграция:** при старте сервера, если `client/data/editor-overrides.json` нет или он старее `shared/editor-overrides.json` (rev/savedAt), он создаётся из `shared` (в логе: `client/data/editor-overrides.json обновлён из shared`). Источник правды — по-прежнему `shared/editor-overrides.json`. В репозиторий клиента добавлен текущий `gm/data/editor-overrides.json` (совпадает с `steam/shared`).
- **Кэш:** `data/editor-overrides.json` и `data/terrain-paint-[12].png` отдаются с `no-cache` + ETag (304, если не менялись).
- **Террейн (E13):** `writeTerrainPaint` проверяет, что слои — настоящие PNG (сигнатура, base64, ≤16 МБ), и пишет все файлы (оба слоя × client/data + shared) во временные, затем `rename`: либо всё, либо ничего. Неверные данные → 400 вместо 500. Так же сделано в обоих серверах (`http/admin-api.js`, `static-http.js`).
- Загрузка иконок и текстур из редактора тоже пишется атомарно.
- Экспорт сцены в редакторе («📋 Экспорт») выдаёт JSON (`editor-overrides.json`) вместо JS-кода.
- Версии: `boot.module.js?v=json-1` (game.html), `?v=e48-json-1` (editor.html), `editor-overrides-data.js?v=json-1`, `editor.js?v=foliage-sel-8`.

## При выкладке
- Выложить клиент целиком (новый `js/editor-overrides-data.js`, `js/boot.module.js`, `game.html`, `editor.html`, `js/editor.js`, `data/editor-overrides.json`).
- **Не перетирать** живой `steam/shared/editor-overrides.json` версией из репозитория — это данные сцены. Клиентская копия при старте сама догонит серверную.
- В CDN: `data/editor-overrides.json` и `data/terrain-paint-*.png` — не кэшировать (или уважать `no-cache`). Правило для `js/editor-overrides-data.js` больше не обязательно.

## Тесты
- `tests/smoke-editor-json.js` (новый, сам поднимает сервер на 3953): 16/16 — создание клиентского JSON при старте, заголовки, загрузчик не меняется при сохранении, client = shared после сохранения, строка `</script>` остаётся данными, не-PNG/битый слой/битый JSON → 400 без изменения файлов, валидные PNG пишутся во все копии, нет временных файлов, кэш в режиме production.
- Обновлены: `smoke-editor-save` (13/13, проверка JSON вместо JS), `smoke-prod` (заголовки JSON).
- Регресс: `smoke-key-secrets` 23/23, `smoke-key-login` 40/40, `smoke-guest-tokens` 19/19 и strict 17/17, `smoke-security` 9/9, `smoke-items` 13/13, `unit-editor-queue`.

# Этап 4.5 — мелочи: токен редактора, регион при телепорте, чистка репо

## Токен редактора больше не в URL (`?k=`)
- Было: ключ редактора добавлялся в URL каждого файла редактора и `/api/editor/session?k=…` → попадал в логи nginx/CDN, `Referer`, историю браузера.
- Стало: клиент один раз делает `POST /api/editor/session` с заголовком `X-Editor-Key`, сервер ставит `HttpOnly; SameSite=Strict` cookie `ps_ed`, дальше файлы редактора грузятся по cookie. Токен из query сервер больше **не принимает** нигде (файлы редактора, сессия, API редактора).
- Cookie получает `Secure`, когда запрос пришёл по https (в т.ч. `X-Forwarded-Proto: https` от nginx). Раньше `Secure` ставился всегда в production — по http cookie не сохранялась, и редактор держался только на `?k=`.
- `boot.module.js?v=json-2` (game.html), `?v=e48-json-2` (editor.html).

## Регион и подписка при телепорте
- Новая функция `updatePlayerRegion(p, {regionId, notify})` в server.js: пересчитывает регион и вызывает `syncPlayerRegionSubscription` (отписка от старого топика `region:*`, подписка на новый).
- Подключена: телепорт у NPC (`npc_teleport`), свиток «в город» (`escapeToCity`), возрождение в деревне, GM `//teleport` (координаты и к игроку), `//goto`, `//recall`. GM-команды раньше вообще не обновляли `p.region`; теперь игроку уходит и пакет `region` (название зоны, мирная/нет).
- Раньше после телепорта игрок до первого шага получал региональные рассылки старой зоны и не получал новой (uWS Pub/Sub).
