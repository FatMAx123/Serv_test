# Ключи игроков и секреты сервера — инструкция

Документ для администратора сервера. Описывает, как устроены ключи входа, какие секреты нужны серверу, как их задать на живом сервере без потери ключей игроков и что делать при проблемах.

---

## 1. Как это устроено (коротко)

| Что | Где хранится | Чем защищено |
|---|---|---|
| **Логин игрока** (с этапа 4.3) | в зашифрованном реестре, в нижнем регистре | не секрет; уникален |
| **Ключ игрока** (вводит в меню вместе с логином) | нигде — сервер хранит только хэш | новые аккаунты: HMAC с `KEY_PEPPER` → **scrypt со своей солью на аккаунт**, регистр букв важен<br>старые аккаунты «только ключ»: HMAC → PBKDF2 → HMAC с `KEY_PEPPER`, без учёта регистра |
| **Реестр ключей** (логин → аккаунт; у старых — хэш ключа → аккаунт) | Postgres: `system_state`, key = `account_keys`<br>файловый режим: `steam/data/account_keys.json` | шифрование AES-256-GCM ключом из `KEY_VAULT_SECRET` |
| **Токен устройства** (выдаётся при вводе ключа, лежит в браузере игрока) | хэши — в профилях персонажей (`guestTokenHashes`) и в записи ключа в реестре | случайные 32 байта; до 5 устройств на аккаунт |

Главное правило: **`KEY_PEPPER` и `KEY_VAULT_SECRET` — это ключи от всех аккаунтов.**
- Потеряли `KEY_VAULT_SECRET` → реестр ключей не расшифровать, ни один игрок не войдёт по ключу.
- Утёк `KEY_PEPPER` вместе с базой → становится возможен перебор ключей офлайн.

## 2. Переменные окружения

### Обязательные в production
| Переменная | Требование |
|---|---|
| `KEY_PEPPER` | ≥ 32 символов, случайный |
| `KEY_VAULT_SECRET` | ≥ 32 символов, случайный, **другой**, чем `KEY_PEPPER` |

Без них (или если они короче 32 символов / совпадают со старыми встроенными значениями) сервер с `NODE_ENV=production` **не запустится**. В логе будет:
```
[AccountKeys] FATAL: секреты ключей не настроены: ...
```
Временный обход (только на время переезда!): `ALLOW_DEFAULT_KEY_SECRETS=1`.

### Для миграции и смены секретов
| Переменная | Назначение |
|---|---|
| `KEY_VAULT_SECRET_OLD` | прежний ключ реестра (при смене `KEY_VAULT_SECRET`) |
| `KEY_PEPPER_OLD` | прежний pepper (при смене `KEY_PEPPER`) |
| `KEY_PREHASH_SALT`, `KEY_KDF_SALT`, `KEY_KDF_ROUNDS` | доп. параметры хэша (необязательны; по умолчанию — прежние значения) |
| `KEY_PREHASH_SALT_OLD`, `KEY_KDF_SALT_OLD`, `KEY_KDF_ROUNDS_OLD` | их прежние значения, если меняли |
| `KEY_ALLOW_OLD_HASHES=0` | перестать принимать ключи со старыми хэшами (финал миграции) |

### Токены устройств
| Переменная | Назначение |
|---|---|
| `GUEST_TOKENS_MAX` (5) | сколько устройств помнить на аккаунт; при превышении самое старое попросит ключ заново |
| `GUEST_LEGACY_TOKENS=0` | перестать принимать старые (вычисляемые) токены |
| `GUEST_TOFU=0` | запретить старым аккаунтам без записанного токена «закрепляться» первым входом |

### Логины (этап 4.3)
| Переменная | Назначение |
|---|---|
| `KEY_ALLOW_KEYONLY=0` | перестать пускать старые аккаунты по одному ключу без логина (финал перехода на логины) |
| `KEY_SCRYPT_N` (16384) | сложность scrypt (степень двойки); увеличение применяется к аккаунту при его следующем входе |
| `KEY_LEGACY_CREATE=1` | только для dev-тестов: создавать аккаунты старого формата. В production игнорируется |

### Прочее
| Переменная | Назначение |
|---|---|
| `KEY_ATTEMPTS_PER_10MIN` (15) | лимит попыток ввода ключа с одного IP за 10 минут |
| — | на каждый логин: 10 неудач за 15 минут (с любых IP) → логин заблокирован на 15 минут |
| `MAX_CONCURRENT_KDF` (3), `MAX_KDF_QUEUE` (10) | защита CPU от массового перебора |

## 3. Первичная настройка на ЖИВОМ сервере (сейчас работает на встроенных секретах)

**Шаг 0. Бэкап.**
- Postgres: `pg_dump` всей базы (минимум — таблица `system_state`).
- Файловый режим: скопировать папку `steam/data/`.

**Шаг 1. Сгенерировать два секрета** (по отдельности):
```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

**Шаг 2. Сохранить их в надёжном месте** (менеджер паролей / секретов хостинга). **Не в репозиторий, не в чат, не в `.env` в git.**

**Шаг 3. Прописать в окружение сервера:**
```bash
KEY_PEPPER=<первый>
KEY_VAULT_SECRET=<второй>
```
`KEY_*_OLD` задавать не нужно — сервер сам знает прежние встроенные значения.
В кластере переменные должны быть одинаковыми у мастера и всех воркеров.

**Шаг 4. Перезапустить и проверить лог.** Должно быть:
```
[AccountKeys] реестр перешифрован текущим KEY_VAULT_SECRET (был: builtin), бэкап: account_keys_backup_builtin
[AccountKeys] ключей на текущих параметрах: 0 из N
[AccountKeys] loaded bindings: N
```
- Бэкап старого реестра сохранён автоматически: Postgres — `system_state` key `account_keys_backup_builtin`, файлы — `steam/data/account_keys_backup_builtin.json`.
- `0 из N` — это нормально: хэши переводятся на новый pepper **постепенно**, когда игрок вводит ключ.

**Шаг 5. Проверить вход:** войти по своему ключу (на другом браузере / в инкогнито). Вход должен пройти, а после перезапуска счётчик станет `1 из N`.

Игрокам ничего делать не нужно: ключи работают как раньше.

## 4. Завершение миграции

### 4.1 Старые хэши ключей
Счётчик в логе при старте: `ключей на текущих параметрах: X из Y`.
Когда X близко к Y (или прошло 1–3 месяца) — задать:
```bash
KEY_ALLOW_OLD_HASHES=0
```
⚠️ Ключи, которые так и не были введены после смены pepper, после этого **перестанут подходить** (игрок с таким ключом получит новый пустой аккаунт). Поэтому не спешить.

### 4.2 Старые токены устройств
Через 2–4 недели после выкладки этапа 4.1 задать:
```bash
GUEST_LEGACY_TOKENS=0
GUEST_TOFU=0
```
Активные игроки к этому моменту уже получили новые токены автоматически. Кто не заходил — войдёт повторным вводом ключа.
Сколько раз срабатывал TOFU, видно по событиям `guest_tofu` в логе модерации.

### 4.3 Вход без логина (этап 4.3)
Счётчик в логе при старте: `аккаунтов с логином: X из Y`. Старые игроки привязывают логин сами (окно после входа по ключу или ввод логина + старого ключа).
Когда X близко к Y (или прошло 2–3 месяца) — задать:
```bash
KEY_ALLOW_KEYONLY=0
```
⚠️ Старые аккаунты без логина после этого **не войдут по ключу** (только по сохранённому токену устройства). Вернуть: удалить переменную, попросить игрока войти ключом и привязать логин.

### 4.4 Встроенные значения больше не нужны
Убедиться, что `ALLOW_DEFAULT_KEY_SECRETS` **не задан**.

## 5. Плановая смена секретов (ротация, например раз в год или после утечки)

### Сменить `KEY_VAULT_SECRET` (быстро, без участия игроков)
```bash
KEY_VAULT_SECRET_OLD=<текущий>
KEY_VAULT_SECRET=<новый>
```
Перезапуск → в логе `реестр перешифрован ... (был: old)`, бэкап `account_keys_backup_old`.
После успешного старта `KEY_VAULT_SECRET_OLD` можно убрать.

### Сменить `KEY_PEPPER` (постепенно, через вход игроков)
```bash
KEY_PEPPER_OLD=<текущий>
KEY_PEPPER=<новый>
```
Дальше — как в п. 4.1: ждать счётчик и только потом `KEY_ALLOW_OLD_HASHES=0` и удаление `KEY_PEPPER_OLD`.
⚠️ Одновременно поддерживается только **одно** предыдущее значение. Не меняйте pepper повторно, пока не закончилась предыдущая миграция.

### При утечке
1. Сменить оба секрета (как выше).
2. Сменить `MOD_SECRET`, `METRICS_TOKEN`, `YANDEX_APP_SECRET` (если могли утечь).
3. Утёкший токен конкретного игрока отзывается сменой его ключа (`/api/auth/set-codeword`) — все его устройства разлогиниваются, выдаётся новый токен.

## 6. Как работают ключи и токены для игрока

- **Вход** (`/api/auth/enter-key`, поля `login`, `key`, `mode`):
  - логин занят → проверяется ключ; верный → вход, устройство получает **новый случайный токен**; неверный → «Неверный логин или ключ»;
  - логин свободен и ключ совпал со старым аккаунтом «только ключ» → этот аккаунт получает логин (перевод, `migrated: true`);
  - логин свободен → создаётся новый аккаунт; если в браузере уже был гостевой аккаунт и игрок доказал владение им (его токеном), персонажи переносятся под него.
  - Ключи у разных аккаунтов могут совпадать — уникален только логин (нет подсказки «ключ занят»).
  - Требования к новому ключу: 6–64 символа ASCII, хотя бы одна заглавная, не простой, не содержит логин. Логин: 3–24 символа `a-z 0-9 _ . -`, регистр не важен.
- **Старый ключ без логина:** игрок вводит только ключ → входит как раньше (регистр не важен), и меню предлагает «Придумайте логин» (можно «Позже»). После привязки вход — только по логину и ключу, **ключ с тем же регистром**, как он ввёл его при привязке.
- **Несколько устройств:** каждое получает свой токен, помнятся последние 5 (`GUEST_TOKENS_MAX`).
- **Смена ключа** отзывает **все** токены аккаунта — со всех устройств нужно войти заново.
- **Старый токен** (выдавался до этапа 4.1) принимается и при первом входе автоматически заменяется новым — клиент сохраняет его сам.

## 7. Проблемы и решения

| Симптом | Причина | Что делать |
|---|---|---|
| Сервер не стартует: `FATAL: секреты ключей не настроены` | production без `KEY_PEPPER` / `KEY_VAULT_SECRET` или они короче 32 символов | задать секреты (п. 3); временно — `ALLOW_DEFAULT_KEY_SECRETS=1` |
| В логе `GCM decryption ... ни один ключ не подошёл`, ввод ключа отвечает «Сервер ключей недоступен» | неверный `KEY_VAULT_SECRET` (опечатка, другой сервер, потерян) | **ничего не удалять** — реестр не тронут. Вернуть правильный секрет или указать прежний в `KEY_VAULT_SECRET_OLD` и перезапустить |
| Потерян `KEY_VAULT_SECRET` | — | восстановить из менеджера секретов. Если он был встроенным — бэкап `account_keys_backup_builtin` открывается без него. Иначе реестр не восстановить |
| `AccountKeys init error` + повтор каждые 10 с | БД недоступна | починить БД; реестр загрузится сам, запись до этого заблокирована (защита от затирания) |
| Игрок: «ключ не подходит» после `KEY_ALLOW_OLD_HASHES=0` | его ключ не мигрировал | временно вернуть `KEY_ALLOW_OLD_HASHES` (удалить), попросить игрока войти, затем снова `=0` |
| Игрок: «просит ключ на одном из устройств» | > 5 устройств или ключ сменили | ввести ключ на этом устройстве ещё раз |
| Игрок без ключа (гость) не входит после `GUEST_TOFU=0` | очень старый профиль без записанного токена | восстановить вручную через админа (выдать ключ / перенести персонажа) |
| Игрок: «Неверный логин или ключ» после привязки логина | вводит ключ в другом регистре (раньше регистр не учитывался) | ввести ключ точно так же, как при привязке логина; если не помнит — восстановление через админа |
| Игрок: «Слишком много неверных попыток для этого логина» | 10 неудач за 15 мин (возможно, кто-то подбирает) | подождать 15 минут; блокировка снимается сама и при перезапуске сервера |
| Новый игрок: «Для нового аккаунта укажите логин» | ввёл только ключ | ввести логин и ключ |
| Счётчик миграции не растёт | игроки не вводят ключ (входят по сохранённому токену) | это нормально: хэш мигрирует только при вводе ключа. Ждать или оставить `KEY_ALLOW_OLD_HASHES` включённым |

## 8. Проверка

```bash
# секреты и перешифровка: сам поднимает сервер в отдельной копии (порт 3950)
node tests/smoke-key-secrets.js

# логины, scrypt, перевод старых аккаунтов: сам поднимает сервер (порт 3951)
node tests/smoke-key-login.js

# токены устройств: нужен запущенный dev-сервер со старым форматом аккаунтов
cd steam && PORT=3940 ALLOW_INSECURE_DEV=1 KEY_LEGACY_CREATE=1 node server/server.js &
cd .. && PORT=3940 node tests/smoke-guest-tokens.js
```
Ожидаемо: `Итого OK=23 FAIL=0`, `Итого OK=40 FAIL=0` и `Итого OK=19 FAIL=0`.
